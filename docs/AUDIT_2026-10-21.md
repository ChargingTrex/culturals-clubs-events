# PRD implementation audit — 2026-10-21

**Question answered:** how much of `Student_Life_Clubs_Events_PRD_V4` (the current PRD; V1 is
the original, V2/V3 identical, V4 adds §5.9 and small edits) is implemented, where, and how
well it is proven.

**Method.** The PRD was split into bullet-level requirements (one row each) across §4, §5.1–5.20,
§6 and §8. Each row was checked against the code with `codegraph explore`, graded
BUILT / PARTIAL / MISSING / DEVIATES-BY-DECISION, given `file:line` evidence and the name of the
test that proves it (or "none"). Decisions recorded in MASTER_SPEC §9 (faculty-advisor gate
removed on purpose, Cultural Society gate added, Vice-Chancellor sees aggregates only) count
as DEVIATES, not MISSING. Both test suites were run. The row-level matrices are in
[`audit-detail-backend.md`](audit-detail-backend.md) and
[`audit-detail-webapp.md`](audit-detail-webapp.md); the knowledge graph is in
`graphify-out/` (2,747 nodes, 6,598 edges, 150 communities, `graph.html`).

## 1. Headline

| Codebase | Requirements | BUILT | BUILT + PARTIAL | Tests |
|---|---:|---:|---:|---|
| Django backend (`clubs-and-culturals-platform/app/backend`) | 247 | 86 (35%) | 173 (70%) | 143 pass (Python 3.12, SQLite) |
| Browser walkthrough (`web-app/`) | 235 | 80 (34%) | 149 (63%) | smoke + 109 e2e pass (Node 24) |
| React frontend (`app/frontend`) | – | **0 — empty directories** | – | none |

Reading the two numbers together: **the rules of the system exist and are tested twice
(server-side and in the browser mirror), but the product the PRD describes is roughly one
third delivered.** What is built is the spine: proposal → three-gate approval → publish →
register → scan → close → settle → semester report. What is missing is almost everything
around that spine: clubs as something students discover and join, succession, feedback,
photos as real media, the operations toolkit, fests, exports, and the React application the
spec fixes as the frontend.

### Delivered and proven (both codebases)
- Sign-in with mandatory second factor for staff; identical claim shape in local and portal SSO modes; refresh rotation with family revocation.
- Role model with scoped club roles; capability payload drives navigation; hiding is not the permission.
- Three-gate approval chain as configuration (Society → Dean → VC), route frozen at submission, comment required to return or reject, no self-approval, MFA above threshold, clash blocks approval.
- Budget: templates with per-head scaling and contingency, explicit nil declaration, lines frozen under review, line-level reduce-only sanction, receipts per line with supersede-never-overwrite, settlement with all blockers at once.
- Attendance: profile QR + one-time pass, seven-branch (plus expired and cancelled) resolution, ScanRecord on every attempt, offline replay with earliest-wins and idempotency, station token bound to one event, treasurer excluded from the door.
- Venue clash detection with buffer, soft clash flagged for the Dean, atomic reassignment with reason.
- Semester report leading with unique students, department snapshot, own vs external never summed; Dean overview with evidence chasing and capture rate.
- Vice-Chancellor sees aggregates only, with a test sweep asserting no PRN or name reaches that role.

### Not delivered (PRD features with no implementation in either codebase)
Waitlist · feedback surveys · office-bearer terms and annual handover · club join requests
(open vs approval) · new-club registration workflow · dormancy auto-flag · personalised feed
and notification preferences · exam blackout periods · per-venue timeline, pressure and
utilisation views · photo gallery as media with consent · social posts as records with
club-level tracking · event templates with task checklists, cloning, reminders, SLA
escalation · custom registration forms, team entries, volunteer roster, speakers, sponsors ·
session-level check-in · auto-drafted event report, certificates, learnings, vendor records ·
approval delegation and per-type chains · fest sub-events, fest page, fest roles, fest
budget envelope · external participant public registration and purge · PDF / PowerPoint / CSV
report, trend vs previous semester, Management dashboard · Student Life Office role ·
attendee list export · any Celery job · the React frontend.

Test coverage: 143 tests, with wrong-role tests for approvals, budget visibility and spend,
role assignment, the door, VC data isolation, venue reassignment and MFA. **No tests at
all** for club CRUD gating, the student registration endpoints over HTTP, scan and
offline-sync over HTTP (the seven-branch tests call the service directly), manual check-in,
notifications, the audit endpoint, template arithmetic, Dean overview contents, event-list
visibility scoping, go-live, photo-required-to-close, or the demo-mode guards.

Other backend findings from the matrix: receipts are written under `media/` but no URL
serves them; roster reads are documented as audited but `EventRosterView` never writes an
audit entry; students are not notified on publication or a venue move; the committed `.env`
carries the placeholder secret key, `DEBUG=1`, `DEMO_MODE=1` and no QR signing key, so the
development key signs every pass. Since the 2026-09-30 gap register, **none of its sixteen
"documented but not built" items has been built.**

## 3. Browser walkthrough — `web-app/`

A no-server ES-module build: the same rules run in the browser against localStorage so
testers can feel the workflow. It defends nothing and is not production, but it is the
only UI that exists, and its role-scoped navigation and refusal behaviour are what the
React app should port.

| Area | Built | Notes |
|---|---|---|
| §5.16 attendance capture | 21 of 26 rows | the strongest area; seven verdicts, reissue, PRN fallback |
| §5.19.2 role matrix, §6.2/6.5 metrics, §5.7.3 sanctioning | strong | mirrors the backend tests |
| §5.1–5.3 clubs, membership, succession | thin | no directory, join or handover |
| §5.8, §5.10, §5.12, §5.15 | thin or absent | feedback, photos, ops toolkit, fests |
| §6.1 report | numbers only | no trend, category split, fest line, highlights, PPTX/CSV |

Bugs found beyond the documented omissions (file references in the detail file):
1. An overspent line can never be settled from the UI: the rule demands a variance note, the budget page has no field for it.
2. A club with no published event is still offered "Scan station" and gets a 404 box; the Treasurer is linked to a station that refuses them.
3. Sanction inputs rendered at the Society and Management gates are ignored; only the Dean stage applies them.
4. Approver return/reject comments are never shown on a club page, and the submitting Secretary is not notified of the outcome.
5. Offline queueing and multi-station exist in the API layer only; the station page never queues and the station id is fixed.
6. README, CONTRIBUTING and package.json say "89 tests"; there are 109.

Deployment: `netlify.toml` is correct for a static publish; no `vercel.json` is needed (an
equivalent is given in the detail file; `cleanUrls` must stay off because links target
`*.html`).

## 4. Cross-cutting findings that change priorities

| # | Finding | Severity | Where |
|---|---|---|---|
| X-1 | **`DELETE /api/v1/events/{id}` has no permission check.** `EventViewSet` is a `ModelViewSet` with `perform_update` guarded but no `destroy` override, so any authenticated user whose event list includes the event (every student for a published event) can hard-delete it; with registrations present the FK `PROTECT` turns it into a 500. | **Critical** | `events/views.py:30` |
| X-2 | **No venue exclusion constraint exists.** `settings.py`, `README.md` and MASTER_SPEC §10.3 all describe a Postgres-only exclusion constraint that "degrades" on SQLite. No migration creates one; no `VenueBooking` model exists. Clash detection is application-level and `EventViewSet.create` checks it outside any lock, so two concurrent proposals can both take a slot. | High | `events/services.py`, `events/migrations/` |
| X-3 | Enum columns are plain `varchar` with Django `choices`; AGENT_PROMPT §4 requires CHECK constraints. | Medium | all `models.py` |
| X-4 | `event_organiser:<id>` is never granted in local mode; only platform-issued tokens can carry it, so the Organiser role the PRD describes cannot be exercised standalone. | Medium | `identity/tokens.py` |
| X-5 | Capture rate is computed two different ways under one name (documents: attended-not-manual / attended; code: accepted scans / all scans). | Medium | `reporting/services.py` |
| X-6 | OpenAPI generation reports 92 errors (20 unique causes) — ad-hoc dict responses with no serializer — so a generated client for the React app would be incomplete. | Medium | `*/views.py` |
| X-7 | No Celery task exists anywhere; everything documented as a job (report generation, dormancy, retention, purge) runs in-request or not at all. | Medium | `config/celery.py` |
| X-8 | No git history at the project root (the two-draft collision in `RECONCILIATION.md` was unrecoverable for that reason). `git init` done today; baseline commit pending. | Process | root |
| X-9 | The directory name contains `:` and a trailing space; Python cannot create a venv inside it and several tools strip the space. Rename recommended. | Process | root |
| X-10 | `CLAUDE.md` and `.claude/skills/` were present at the start of this session and are gone now; not removed by this session. | Process | root |

## 6. What the knowledge graph says

God nodes: the PRD documents themselves (V1–V3, ~170–200 edges each), `ProblemDetail`,
`db()` (web-app), `as_user()` (test helper), Event Flows, `EventStatus`, the Decision Log.
`EventStatus` bridges 20 communities, which is the structural reason every feature touches
the event status machine. Surprising-connection edges are all the documents restating each
other (AGENT_PROMPT ↔ MASTER_SPEC ↔ RECONCILIATION) — the rules are consistent across
documents, and the gaps are in breadth, not contradiction. One AMBIGUOUS link worth a
decision: the Decision Log marks the faculty-advisor gate superseded while the PRD still
routes through it (§5.4, §5.7.3, §5.19.1). Graph health: 300 dangling-endpoint and 199
collapsed edges from re-extracted documents; the graph is usable, the duplicates are
cosmetic.

## 7. Recommendation

Treat the backend as the product and the web-app as the reference UI. Fix X-1 and X-2
first (hours). Then close the backend gaps in the order of the completion plan, build the
React frontend against a clean OpenAPI schema, and host the test stack on Vercel (backend +
React) and Netlify (walkthrough). The plan, agent split and checklist are in
[`COMPLETION_PLAN.md`](COMPLETION_PLAN.md) and [`CHECKLIST.md`](CHECKLIST.md).
